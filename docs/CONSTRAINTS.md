# 移动端智能客服底座 MVP 工程约束

> 文档性质：项目级强制约束文件  
> 文档版本：1.1.0  
> 生效日期：2026-09-23  
> 适用范围：本仓库内移动端智能客服底座 MVP 的设计、开发、测试、演示与验收  
> 约束状态：生效  

## 1. 文档目的

本文件是本项目开发与验收的工程合同，用于把需求转化为明确、可验证、可追踪的约束。

所有开发工作必须遵守本文件。功能“能够运行”不等于符合要求；只有同时满足对应约束、通过规定验证并提供可复核证据，才可判定完成。

本文件中的关键词含义如下：

- **必须**：强制要求，不满足即验收失败。
- **禁止**：不得出现的实现或行为，违反即验收失败。
- **应当**：原则上必须满足；如不能满足，必须在验收前记录原因、影响和替代措施并获得确认。
- **可以**：不影响验收的可选实现。

## 2. 依据与优先级

### 2.1 需求依据

本文件依据以下现有文档制定：

1. `target.md`：本周 MVP 任务书，是本期范围和验收标准的直接来源。
2. `request.md`：系统整体解决方案，是长期业务和架构背景。

### 2.2 冲突处理顺序

发生冲突时，按以下顺序执行：

1. 经负责人确认并已生效的本文件最新版本；
2. `target.md` 中的本周 MVP 要求；
3. `request.md` 中的长期方案；
4. 其他设计说明、临时建议和口头约定。

任何人不得通过代码实现、测试修改或口头说明，静默降低本文件中的约束。

### 2.3 约束变更

约束需要新增、删除或降低时，必须同时记录：

- 变更内容；
- 变更原因；
- 影响范围；
- 对测试与验收的影响；
- 确认人；
- 生效日期；
- 文档版本变化。

未经确认的约束变更不生效。修正文案、错别字且不改变含义的修改，可以只递增补丁版本。

## 3. 本期范围与非目标

### 3.1 本期必须形成的业务闭环

本期必须交付一套可在手机浏览器或微信内置浏览器演示的移动端 H5 底座，并完整覆盖以下闭环：

1. 知识文档上传、切片、向量化和入库；
2. 基于知识库的 RAG 问答，并显示引用来源；
3. 无知识依据时拒答并提示转人工；
4. 最近 3～5 轮的多轮对话记忆；
5. 公开知识与内部知识的角色权限隔离；
6. 自然语言触发 LIMS 订单查询 Mock，并以移动端卡片展示；
7. 对话日志持久化；
8. 可按文档在同网段手机上复现和演示。

### 3.2 本期非目标

以下内容属于长期方案，不是本期 MVP 的强制交付内容：

- 对接真实生产 LIMS；
- 修改、删除或回写 LIMS 数据；
- 部署生产级 MySQL 或 Milvus 集群；
- 大模型训练或行业微调；
- 完整的五类角色和组织级 RBAC；
- 百万级文档容量和生产级高可用；
- 文档版本对比、审批流和复杂运营后台；
- Word、Excel 等任务书未要求的上传格式；
- 生产环境上线、等保或正式安全认证。

可以为以上能力预留接口，但不得以此替代本期闭环，也不得因过度设计影响本期验收。

## 4. Harness 工程约束

### HAR-001 约束先于实现

- 开发任务必须能够对应到本文件中的一个或多个约束编号。
- 不得实现无法说明需求来源、且会显著增加复杂度的功能。
- 发现需求遗漏或冲突时，必须先更新并确认约束，再按新约束开发。

**验证方式：** 代码评审时抽查功能与约束编号的对应关系。

### HAR-002 环境必须可复现

- 项目必须锁定直接依赖版本，并保留可重复安装所需的依赖清单或锁文件。
- 运行所需配置必须通过环境变量或配置文件注入。
- 必须提供不含真实密钥的环境变量示例。
- 禁止依赖某位开发者电脑上的绝对路径、全局安装包、私有临时文件或未说明的手工操作。

**验证方式：** 在未配置本项目的环境中，依据仓库文档完成安装和启动。

### HAR-003 工程入口必须统一

项目完成时必须提供清晰且固定的以下入口：

1. 安装依赖；
2. 启动后端；
3. 启动移动端；
4. 执行代码检查；
5. 执行自动化测试；
6. 执行构建；
7. 执行验收检查。

入口可以由包管理器命令或脚本提供，但必须写入 README，禁止只存在于口头说明中。

**验证方式：** 按 README 从零执行所有入口。

### HAR-004 验收数据必须固定

- 必须提供至少 3 份脱敏样例知识文档。
- 样例必须同时包含公开知识和内部知识。
- 必须提供固定的有效 Mock 订单 `ORD2026001`。
- 必须提供不存在订单的可重复验证场景。
- 测试不得依赖实时变化、来源不明或不可重复获取的数据。

**验证方式：** 清空本地运行数据后，使用仓库样例重新完成入库和测试。

### HAR-005 验证必须自动化优先

- 可以自动验证的行为必须优先使用自动化测试。
- 视觉、真机键盘、微信内置浏览器等不适合完全自动化的行为，必须有明确的人工验收步骤。
- 禁止仅以开发者口头说明或单次成功截图代替可以自动化的测试。

**验证方式：** 检查测试集合、人工验收步骤和约束覆盖关系。

### HAR-006 结果必须有证据

验收时，每个强制约束必须至少具备一种可复核证据：

- 自动化测试结果；
- 接口响应；
- 数据库记录；
- 构建结果；
- 真机操作记录或截图；
- 按步骤复现的人工验收记录。

**验证方式：** 按约束编号抽查证据，证据不得依赖已丢失的临时环境。

### HAR-007 失败必须可见

- 接口异常不得伪装成成功结果。
- 前端必须展示可理解的失败状态，并提供重试能力。
- 自动化检查失败时必须返回失败状态，禁止吞掉错误后继续报告成功。
- 不得通过跳过、删除或弱化测试来获得通过结果。

**验证方式：** 人为制造网络或接口失败，检查界面和测试退出结果。

## 5. 仓库与架构约束

### ARC-001 基本目录边界

项目必须保持以下职责边界：

- `mobile/`：移动端 H5；
- `backend/`：后端接口、RAG、权限、Mock 和日志；
- `data/knowledge/`：知识样例或知识数据入口；
- `docs/`：项目、架构、接口和验收说明。

业务代码不得散落到数据目录或文档目录。生成文件、缓存、数据库运行文件不得与源代码混放。

**验证方式：** 仓库结构审查。

### ARC-002 前后端通过接口协作

- 移动端不得直接读取或修改后端数据库文件。
- 检索、权限判断、订单查询和日志持久化必须由后端执行。
- 后端错误必须使用稳定、可解析的响应结构返回。

**验证方式：** 架构审查与接口测试。

### ARC-003 外部能力必须可替换

- 大模型、向量检索和 LIMS Mock 必须有明确的模块或接口边界。
- 业务流程不得与单一供应商 SDK 深度耦合。
- 缺少真实大模型密钥时，应当能够运行不泄露数据的开发或测试替代路径，但不得把替代结果冒充真实模型结果。

**验证方式：** 配置审查，并在测试配置下执行核心测试。

### ARC-004 数据持久化边界

- 本期对话日志必须写入 SQLite。
- 运行数据库文件不得提交到源码版本库。
- 数据库初始化必须可重复执行。
- 测试数据与开发运行数据必须隔离，测试不得污染演示数据。

**验证方式：** 数据库检查、重复初始化测试和仓库文件检查。

### ARC-005 Gin 后端基线

- 本期后端必须使用 Go 与 Gin 实现，依赖由 `backend/go.mod` 和 `backend/go.sum` 锁定。
- 服务启动入口必须位于 `backend/cmd/server/`，路由与 Handler 必须保持职责分离。
- Day 1 移动端 H5 必须由 Gin 同源托管，使页面和接口可通过一个局域网地址访问。
- `main.go` 只负责配置、组装与启动，不得堆积具体接口业务逻辑。
- 后端必须监听局域网可达地址，不得仅监听 `127.0.0.1`。

**验证方式：** 执行 `go test ./...`，启动服务后分别访问移动端首页、`GET /health` 和 `POST /chat`。

## 6. 移动端约束

### MOB-001 真机访问

手机与开发机处于同一局域网时，必须能通过开发机局域网地址打开 H5 并走通完整主流程。服务不得只监听本机回环地址。

**验证方式：** 真机通过 Wi-Fi 访问，不使用桌面浏览器设备模拟作为唯一证据。

### MOB-002 竖屏优先

- 必须优先适配 375～430 CSS 像素宽度。
- 页面必须包含顶栏、中间消息流和底部输入区域。
- 页面不得只是桌面页面等比例缩小。
- 主要信息在竖屏下不得发生横向溢出或必须横向滚动才能操作。

**验证方式：** 375、390、430 像素视口检查，并至少使用一台真机验证。

### MOB-003 触控可用性

- 主要按钮、输入框操作区和可点击控件的触控尺寸不得小于 44×44 CSS 像素。
- 核心功能不得依赖鼠标悬停。
- 输入框、发送、重试、展开引用和角色切换必须可以单手触控完成。

**验证方式：** 页面尺寸检查与真机操作。

### MOB-004 聊天交互状态

聊天页必须具备：

- 用户与系统消息气泡；
- 消息时间；
- 发送中或加载中状态；
- 请求失败提示；
- 失败重试；
- 首次进入时的空状态；
- 防止用户重复提交导致重复消息的机制。

**验证方式：** 正常、慢响应和失败场景测试。

### MOB-005 移动键盘适配

软键盘弹出后，当前输入框和发送按钮必须保持可操作，最近消息不得被永久遮挡；键盘收起后布局必须恢复正常。

**验证方式：** Android 或 iOS 真机输入测试。

## 7. 后端接口约束

### API-001 健康检查

后端必须提供 `GET /health`。服务正常时必须返回成功状态和稳定的可解析响应，不得依赖大模型调用才能成功。

**验证方式：** 接口自动化测试。

### API-002 聊天接口

后端必须提供 `POST /chat`，请求至少能够表达：

- 用户问题；
- `sessionId`；
- 当前角色。

响应必须能够表达：

- 回答正文；
- 回答类型；
- 引用来源；
- 订单卡片数据（适用时）；
- 可稳定识别的错误信息（失败时）。

**验证方式：** 请求契约和接口自动化测试。

### API-003 文档管理接口

必须具备文档上传和文档列表查询能力。上传失败、格式不支持和内容为空必须返回明确错误，不得伪装成入库成功。

**验证方式：** 支持格式、非法格式、空文件和列表查询测试。

### API-004 输入边界

- 所有接口必须校验必填字段、字段类型和合理长度。
- 文件上传必须限制允许的扩展名和合理大小。
- 文件名不得被直接用作不受控的文件系统路径。
- 客户端传入的角色、权限或文档可见性不得在未校验时直接信任。

**验证方式：** 非法输入和越权接口测试。

## 8. 知识入库约束

### KB-001 支持的文件格式

本期必须支持 PDF、TXT 和 MD。是否支持其他格式不得影响这三种格式的验收。

**验证方式：** 每种格式至少上传一份有效样例。

### KB-002 文档元数据

每份入库文档必须记录：

- 稳定文档标识；
- 原始文件名；
- 品类：纺织、鞋类或杂货；
- 类型：标准、业务规范或 FAQ；
- 权限：公开或内部；
- 入库时间；
- 切片数量或可验证的处理结果。

**验证方式：** 入库后通过列表接口或持久化数据检查。

### KB-003 切片与向量化

- 文档必须经过文本提取、切片和向量化后才可标记为入库成功。
- 空文本、解析失败或向量化失败不得标记为成功。
- 切片必须保留到原文档的来源关联，以支持引用追溯。

**验证方式：** 成功、空文档和解析失败测试；抽查切片来源。

### KB-004 最低数据量

演示和验收环境中必须成功入库不少于 3 个文件，并可通过列表接口查询。

**验证方式：** 清空后重新入库固定样例，并查询列表。

## 9. RAG 与防幻觉约束

### RAG-001 检索后生成

知识问答必须按“问题 → 权限过滤 → Top-K 检索 → 基于检索片段生成 → 返回引用”的顺序执行。

禁止绕过知识库直接使用通用模型知识回答检测专业问题，并将其展示为有知识库依据的答案。

**验证方式：** 流程审查和可控样例测试。

### RAG-002 仅依据检索内容

提供给生成模型的指令必须明确要求只依据本次允许访问的检索片段回答。答案中的关键结论必须能够在返回的引用片段中找到依据。

**验证方式：** 使用内容唯一且可核对的样例文档进行问答测试。

### RAG-003 引用来源

- 命中知识库的回答必须返回至少一个引用来源。
- 移动端必须显示答案正文和可展开、可收起的引用区域。
- 引用至少显示原始文件名。
- 引用不得包含当前角色无权访问的文件。

**验证方式：** 接口测试、权限测试和移动端真机操作。

### RAG-004 固定拒答

检索为空或最高相似度低于配置阈值时，不得调用检索外知识补全答案，必须返回：

> 知识库暂无依据，请转人工

拒答场景不得附加虚构引用。

**验证方式：** 使用与知识库无关的问题执行自动化测试和真机演示。

### RAG-005 阈值和 Top-K 可配置

相似度阈值与 Top-K 不得散落为多个互相冲突的魔法数，必须由集中配置管理，并具有安全默认值。

**验证方式：** 配置和代码审查。

## 10. 会话与日志约束

### SES-001 会话标识

- 每段会话必须使用稳定的 `sessionId`。
- 移动端必须将 `sessionId` 保存在 `localStorage`，刷新后继续使用同一会话。
- 不得仅依赖进程内存维持会话标识。

**验证方式：** 刷新页面后继续提问，检查会话连续性。

### SES-002 多轮范围

生成回答时必须携带最近 3～5 轮相关对话。不得无限累积全部历史并发送给模型。

**验证方式：** 构造超过 5 轮的对话并检查上下文边界。

### LOG-001 对话日志

每次完成的问答必须写入 SQLite，至少记录：

- `sessionId`；
- 角色；
- 用户问题；
- 系统答案；
- 引用文档；
- 回答类型；
- 创建时间。

失败请求应当记录足够的诊断信息，但不得记录密钥等敏感数据。

**验证方式：** 完成问答后查询数据库记录。

## 11. 角色与权限约束

### AUTH-001 最小角色集合

本期至少必须提供以下角色：

- 外部客户；
- 客服；
- 管理员。

验收时至少要能明显展示两种角色之间的检索范围差异。

**验证方式：** 角色切换和相同问题对比测试。

### AUTH-002 文档权限过滤

- 外部客户只能检索权限为“公开”的文档。
- 客服和管理员可以按本期定义检索内部文档。
- 权限过滤必须发生在生成答案之前。
- 禁止先检索内部内容，再仅在界面上隐藏引用。

**验证方式：** 使用仅存在于内部文档中的唯一内容进行越权测试。

### AUTH-003 后端强制授权

权限判断必须在后端执行。隐藏前端入口不能作为权限控制。即使绕过界面直接调用接口，外部客户也不得获得内部文档、切片、引用或由内部内容生成的答案。

**验证方式：** 直接调用接口执行越权测试。

### AUTH-004 演示身份边界

本期角色选择可以是演示级入口，但界面和文档必须明确其非生产身份认证。不得宣称已实现生产级登录或安全认证。

**验证方式：** 界面、说明和实现一致性检查。

## 12. LIMS Mock 约束

### LIMS-001 自然语言触发

系统必须能够从类似“查一下订单 ORD2026001”的自然语言中识别订单查询意图和订单号。

**验证方式：** 至少使用直接表达、带礼貌词表达和不存在订单三类输入测试。

### LIMS-002 固定 Mock 订单

必须提供订单 `ORD2026001` 的稳定 Mock 数据，至少包含：

- 订单号；
- 订单状态；
- 检测进度；
- 报告状态。

**验证方式：** 重复查询并核对响应结构与内容稳定性。

### LIMS-003 移动端卡片

有效订单必须以移动端卡片展示，不得仅返回一段无结构文本。卡片在 375 像素宽度下不得横向溢出。

**验证方式：** 375 像素视口和真机检查。

### LIMS-004 查询安全边界

- 本期 LIMS 仅为 Mock，只允许查询。
- 禁止连接、修改或删除真实 LIMS 数据。
- 不存在的订单必须返回明确的未找到状态，不得生成虚假订单信息。

**验证方式：** 实现审查和不存在订单测试。

## 13. 安全与隐私约束

### SEC-001 密钥管理

- API 密钥、密码、令牌和其他凭据不得写入源代码、测试数据、日志或提交记录。
- 必须通过环境变量或不入库的本地配置提供真实凭据。
- 示例配置只能包含占位值。

**验证方式：** 仓库内容和提交历史检查。

### SEC-002 数据脱敏

- 样例知识、订单、日志和截图必须使用脱敏或虚构数据。
- 禁止把真实客户身份、联系方式、报告内容或实验数据作为演示数据提交。

**验证方式：** 样例数据和验收材料审查。

### SEC-003 上传安全

- 仅接受允许格式的文件。
- 上传文件必须使用服务端生成或安全处理后的存储名称。
- 必须阻止路径穿越和危险文件覆盖。
- 文件解析失败不得影响服务持续运行。

**验证方式：** 非法扩展名、特殊文件名和损坏文件测试。

### SEC-004 输出边界

接口错误和页面错误不得暴露密钥、完整系统提示词、服务器绝对路径或不必要的堆栈信息。

**验证方式：** 失败场景响应审查。

## 14. 质量与测试约束

### QA-001 最低测试数量

必须形成不少于 15 条可执行测试用例，覆盖：

- 健康检查；
- 文档上传；
- 文档列表；
- 知识命中；
- 引用来源；
- 无依据拒答；
- 公开与内部权限；
- 越权访问；
- 多轮对话；
- 刷新续聊；
- 有效订单；
- 不存在订单；
- 移动端布局；
- 失败重试；
- 对话日志。

测试用例必须包含前置条件、操作步骤、预期结果和实际结果记录位置。

**验证方式：** 用例数量和覆盖审查。

### QA-002 自动化最低覆盖

以下行为必须有自动化测试，不得只做人工点击：

- `GET /health`；
- `POST /chat` 的基础契约；
- 文档上传和列表；
- RAG 命中并返回引用；
- RAG 无依据拒答；
- 外部客户无法访问内部知识；
- 有效和无效 Mock 订单；
- 对话日志写入。

**验证方式：** 运行完整自动化测试集合。

### QA-003 回归要求

每次修改业务代码后，必须至少执行与修改范围直接相关的测试；合并或最终交付前必须执行全部代码检查、自动化测试和构建。

禁止在未说明原因的情况下跳过失败测试。

**验证方式：** 检查最终测试和构建结果。

### QA-004 确定性

自动化测试不得依赖公网实时内容或不受控的大模型自由输出。涉及大模型的测试必须通过固定替代实现、录制响应、结构断言或其他可重复方式验证。

**验证方式：** 断网或测试配置下重复运行关键测试。

## 17. 标准演示路径

最终演示必须至少完整执行一次以下路径：

1. 手机扫码或输入局域网地址打开 H5；
2. 以内部联系人角色提出样例知识问题；
3. 展开并核对引用文件名；
4. 提出与知识库无关的问题，看到固定转人工提示；
5. 切换为外部客户，验证无法获取内部知识；
6. 输入“查一下订单 ORD2026001”；
7. 查看订单号、状态、进度和报告状态卡片；
8. 查看本次对话日志记录。

演示过程中不得临时修改数据库、代码或配置来制造通过结果。

## 18. 完成定义

一项功能只有同时满足以下条件，才能标记为完成：

1. 对应至少一个约束编号；
2. 正常流程已经实现；
3. 关键异常流程已经处理；
4. 权限和数据边界已经验证；
5. 应有的自动化测试已经通过；
6. 需要人工验证的场景已有明确步骤；
7. 相关文档与实际实现一致；
8. 未引入明文密钥或真实敏感数据；
9. 全量检查、测试和构建通过；
10. 可以提供可复核的验收证据。

只完成页面、只完成接口、只在开发者电脑上运行成功，或只通过演示但无法复现，均不视为完成。
